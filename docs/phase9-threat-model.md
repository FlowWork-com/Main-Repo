# Phase 9 Threat Model — FlowWork Main Repo

**Last reviewed:** 2026-11-02  
**Scope:** current planning, durable workflow, tool execution, provider, OAuth and staging infrastructure in `FlowWork-com/Main-Repo`.  
**Environment evidence:** isolated FlowWork Staging project `flfwtsxuvzyuotltfrbt`; this document does not authorize production deployment.

This is an engineering threat model based on the checked-in code, migrations, tests and staging evidence. It is not an external penetration test or a certification. Each row separates existing controls from residual verification.

## Trust boundaries

1. **Browser/user → Edge Function:** request bodies and user-provided task content are untrusted. Authentication and exact workspace membership are checked server-side.
2. **Model/provider → planner/FinNLP:** model output, structured JSON, retrieved news and user-supplied excerpts are untrusted data. They cannot define the tool registry, grant permissions or approve actions.
3. **Edge Function → database/RPC:** database functions validate the authenticated actor, resource ownership, workflow state and/or service-role context. Client roles do not receive direct write access to execution history or provider secret tables.
4. **Edge Function → external provider:** credentials and configured provider endpoints remain server-side. Provider errors and content must be bounded and sanitized.
5. **Worker → workflow state:** run/step claims are durable and lease-bound. A timeout or expired lease is treated as ambiguous until reconciled; it is not an automatic retry signal.

## Operational decision log

- The successful authenticated staging smoke proves the safe planning/proposal boundary only. It intentionally does not accept the plan or execute a tool.
- The current Supabase security adviser reports leaked-password protection disabled. It was not available on the reviewed Free plan. This remains a deferred security risk; no bypass is acceptable.
- Alert thresholds and SLO values in `docs/phase9-operational-controls-proposal.md` are proposals, not approved policy or configured alerts.
- Retention periods in that proposal are candidates, not active deletion settings.
- Invoice extraction, Finnhub connection lifecycle and Google OAuth live acceptance remain unverified.

## Exit criteria still open

1. Triage the exact npm audit findings and document fixes or an explicit exception.
2. Finish the authenticated SECURITY DEFINER function review and cross-workspace negative test matrix.
3. Complete end-to-end task/plan/run/step/request/execution correlation and reproducible reliability metrics.
4. Run synthetic staging exercises for hostile files, duplicate dispatch, worker concurrency and ambiguous recovery.
5. Obtain owner approval for alert/SLO and retention policy; configure and test the chosen operational controls.
6. Complete live acceptance only for integrations explicitly in release scope.
7. Record release owner, on-call owner, risk acceptance, recovery point and rollback owner before any production decision.

**No threat-model row authorizes a new integration, arbitrary tool, autonomous approval, or production credential.** Every future change must retain the core invariant: a model proposal is not an action; a tool result is not verification; a task is not complete until workflow state records verified completion.
