# FinNLP financial verification sidecar

## Role

FinNLP is a specialist verifier and financial-language decoder. It is not FlowWork's primary planner, does not own workflow state, and cannot authorize or execute actions. It returns a structured review and a concise handoff message for the main agent.

Use it when a task contains a financial statement, financial terminology, an agent-generated draft answer, or a potentially ambiguous numeric/accounting interpretation. It can:

- Explain financial terms in plain language and identify competing interpretations.
- Compare a claim or draft answer with specifically supplied evidence and the bounded company-news records retrieved from Finnhub.
- Flag supporting, conflicting, mixed, and uncheckable claims with source IDs.
- Ask the main agent for missing units, reporting periods, currency, accounting basis, or other context instead of guessing.
- Return a compact handoff note so the main agent can revise its task result, state limitations, or request clarification.

The reviewer is a second opinion, not an oracle. Finnhub news is provider-retrieved content, not independently fact-checked truth. Evidence supplied by a user or another agent is labelled unverified. The verifier can help find ambiguity and contradictions; it cannot guarantee financial accuracy.

## Planning-time talk-back loop

When the primary planner proposes a plan for a goal or draft that appears financial, the server can make exactly one bounded call to this reviewer, pass the original goal and a size-limited textual summary of the proposed plan, and then give the resulting handoff back to the primary planner for exactly one refinement. There is no recursive agent loop. The refined plan is revalidated with the canonical tool registry and task/goal checks before being saved.

The planning-time pass intentionally has an empty source list: it can decode a phrase such as "year over year", identify missing accounting bases or periods, ask for primary evidence, and challenge unsupported wording, but it **must not certify the factual figure**. The plan stores the reviewer status, ambiguity/questions, and evidence caveat in its limitations. Source-backed review is available through the registered `finnlp-financial-review` tool when explicit source snippets or the bounded Finnhub ticker/date request are supplied. User-provided snippets remain unverified. If the reviewer is missing, times out, returns malformed output, or the main planner cannot apply the feedback, the original plan is retained with a limitation that clearly says the specialist feedback was not applied or no verification took place.


## Tool contract

Tool ID: `finnlp-financial-review`, version `1.0.0`.

Required input: `claim` (up to 2,000 characters).

Optional input:
- `draftAnswer` (up to 4,000 characters) to review another agent's proposed wording.
- `evidence`: at most five objects with `id`, `title`, optional HTTPS `url`, and bounded `excerpt`. User-supplied snippets remain explicitly unverified.
- `ticker`, `startDate`, and `endDate`, which must be supplied together. This retrieves current company-news evidence over an inclusive range of at most 31 days ending today or earlier.

The output contains a review status, plain-language decoding, a bounded set of findings and ambiguities, exact source IDs, follow-up questions, and `handoffMessage` for the main agent. It records qualitative model confidence only as a non-calibrated self-assessment. Supported/contradicted statuses are downgraded when source-linked provider evidence is missing. The source list is generated by the tool, not by the model, so the model cannot introduce arbitrary citation URLs.

## Provider configuration

Configure a separate OpenAI-compatible reviewer in the server-side Supabase Edge Function environment:

- `FLOWWORK_FINNLP_REVIEW_PROVIDER=openai-compatible`
- `FLOWWORK_FINNLP_REVIEW_BASE_URL=https://api.example.com/v1`
- `FLOWWORK_FINNLP_REVIEW_MODEL=<configured-financial-review-model>`
- `FLOWWORK_FINNLP_REVIEW_API_KEY=<server-side-review-key>`

Use a trusted HTTPS endpoint in hosted environments. HTTP is accepted only for loopback local development. The endpoint is completed with the fixed `/chat/completions` path; the tool does not accept a user/model-supplied host or route. The reviewer call has a timeout, request-size bound, response-size bound, redirect rejection, safe provider error mapping, and output schema validation. CI uses mocked fetch and never requires a live reviewer key.

For ticker-backed reviews, the authenticated user's existing Finnhub connection is used through the server-side `read_finnlp_api_key` RPC, scoped to that execution's workspace/member. If the connection is missing, revoked, rate-limited, or the provider fails, the tool returns a sanitized failure and does not fabricate a review or claim that news was checked.

## Data and safety boundaries

- Provider API keys remain server-side; neither key nor raw provider error is returned.
- No trade, order, portfolio mutation, financial transaction, email, CRM write, or external business-record write is implemented.
- The full review result is persisted only through FlowWork's existing task-tool execution record and carries a `financial-review` evidence reference. No extra raw-content table or log is introduced.
- Claims, draft answers, and supplied evidence snippets are sent to the separately configured review model. Configure a provider authorized to process the business data users submit.
- Article snippets and user-supplied evidence are untrusted data, never instructions. The reviewer cannot modify plan approval, task status, or execution policy.
- A positive source assessment is not an investment recommendation or proof of the financial claim. Humans must verify material conclusions and resolve open questions.
- A review result is not execution approval. The main agent must continue to use FlowWork's existing approved plan/run controls; verification remains separate.

## Tests

The unit tests cover bounded input, unsafe URLs/credential-like values, citation allow-listing, unverified-source labelling, ticker/date constraints, unavailable providers, and safe persistence evidence. Deno tests cover server-side configuration, a fixed configured endpoint, timeouts, provider status errors, and credential-safe failures.

No live financial review provider call is made in CI. A staging smoke test using a dedicated safe claim and explicitly configured reviewer/Finnhub credentials is still required to verify production provider behavior.
